# CyTube Knowledge Base — Test Artifact Creation Standard

## Purpose

This document defines how runtime reverse-engineering tests should be created, executed, and archived so that the knowledge repository preserves the **actual executable test**, the **actual runtime output**, and the **interpretation of the evidence** separately.

## Principle: three artifacts, not one

Every significant test should produce three distinct artifacts:

1. **Test script** — the exact JavaScript pasted into Kiwi DevTools.
2. **Test output** — the exact serialized output produced by that execution.
3. **Findings** — human-readable interpretation of what the output proves, what it does not prove, and what should be tested next.

The test script must contain rich comments explaining its purpose, safety, collection method, expected observations, and restoration behavior. This makes the script independently understandable months later.

## Runtime test structure

A test should normally contain these sections:

- Header banner
- TEST ID
- PURPOSE
- WHAT THIS TEST DOES
- WHAT THIS TEST DOES NOT DO
- EXPECTED OBSERVATION
- SAFETY / SIDE EFFECTS
- DATA COLLECTION
- OUTPUT STORAGE
- RESTORATION / CLEANUP
- Main implementation
- Final status marker

## Mobile clipboard rule

On the Kiwi Android DevTools environment, asynchronous clipboard writes are unreliable. Therefore tests should **store their completed result in a global object** such as `window.__WS069_DATA__`.

A separate, synchronously executed DevTools command should copy that object:

```javascript
copy(JSON.stringify(window.__WS069_DATA__,null,2))
```

This separation is intentional. The copied output should be the exact data structure produced by the test, rather than manually selected console text.

## Provenance rule

The repository should distinguish:

```text
WS-069-...-TEST.js
        = exact executable command

WS-069-TEST-OUTPUT.txt
        = exact output captured from the real runtime

WS-069-...-FINDINGS.md
        = interpretation of that real output
```

If a test was generated by ChatGPT but its output was executed by the user, the script and output are still separate evidence artifacts. Never represent an inferred or reconstructed output as if it were the user's actual runtime output.

## Recommended workflow

```text
1. Design test
2. Write richly commented JS test
3. User pastes exact JS into Kiwi DevTools
4. Test stores result in window.__WSxxx_DATA__
5. User runs synchronous copy command
6. User pastes exact output back into conversation
7. Output is archived verbatim
8. Findings are derived from the actual output
9. Findings are archived
10. Next test is designed from evidence
```

This is the canonical evidence chain for the CyTube knowledge base.
