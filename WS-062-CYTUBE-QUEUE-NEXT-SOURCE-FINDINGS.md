# WS-062 — CyTube Queue Next Source Findings

## Test

`WS-062`

## Runtime source captured

The live page exposed the following `playlistMove()` implementation:

```javascript
function playlistMove(from, after, cb) {
    var lifrom = $(".pluid-" + from);
    if(lifrom.length == 0) {
        cb(false);
        return;
    }

    var q = $("#queue");

    if(after === "prepend") {
        lifrom.hide("blind", function() {
            lifrom.detach();
            lifrom.prependTo(q);
            lifrom.show("blind", cb);
        });
    }
    else if(after === "append") {
        lifrom.hide("blind", function() {
            lifrom.detach();
            lifrom.appendTo(q);
            lifrom.show("blind", cb);
        });
    }
    else {
        var liafter = $(".pluid-" + after);
        if(liafter.length == 0) {
            cb(false);
            return;
        }
        lifrom.hide("blind", function() {
            lifrom.detach();
            lifrom.insertAfter(liafter);
            lifrom.show("blind", cb);
        });
    }
}
```

## Critical Queue Next source

`addQueueButtons(li)` exposes the exact Queue Next handler:

```javascript
if(hasPermission("playlistmove")) {
    $("<button/>").addClass("btn btn-xs btn-default qbtn-next")
        .html("<span class='glyphicon glyphicon-share-alt'></span>Queue Next")
        .on('click', function() {
            socket.emit("moveMedia", {
                from: li.data("uid"),
                after: PL_CURRENT
            });
        })
        .appendTo(menu);
}
```

The runtime stack identified the handler at `https://cytu.be/js/util.js:547`.

## Important UID distinction

The values `235` and `242` should **not** be described as playlist array indexes merely because the handler names its parameters `from` and `after`.

`makeQueueEntry(item, addbtns)` assigns:

```javascript
li.addClass("pluid-" + item.uid);
li.data("uid", item.uid);
```

`playlistMove()` then addresses DOM entries using `.pluid-<uid>` and Queue Next obtains `from` through `li.data("uid")`.

Therefore these are **playlist item UIDs**, not necessarily positional indexes.

`after: PL_CURRENT` is the UID of the current playlist item.

## Semantic interpretation

Queue Next means:

> Move the selected playlist item so that it is immediately after the currently playing/current playlist item.

For WS-061:

```text
selected item UID = 235
current item UID  = 242

moveMedia {
    from: 235,
    after: 242
}
```

The client-side `playlistMove()` implementation uses those UIDs to locate DOM entries and inserts the selected entry immediately after the current entry.

## Evidence level

This is now a **runtime + source-confirmed protocol mapping**:

1. WS-061 correlated exactly one user click on `.qbtn-next` with exactly one outbound `moveMedia` event.
2. WS-062 captured the live `addQueueButtons()` source showing Queue Next directly emits `moveMedia`.
3. WS-062 captured `makeQueueEntry()` showing playlist DOM entries and button data are keyed by `item.uid`.
4. WS-062 captured `playlistMove()` showing `from` and `after` are used as playlist UIDs/selectors.
